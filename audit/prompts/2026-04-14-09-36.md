## Analysis

### Why the previous approach was incomplete

The previous commit's `flat_law()` called `_python_gravity_flat_law(data, ...)`
without converting `data` from whatever format it arrived in (numpy arrays,
JAX arrays, etc.) to Python lists. `law()` was not overridden at all, so for
a python-factory `TrueLawModel`, calling `law(numpy_system)` would:
1. Call base class `law()` which does `system.data.flatten()` (fine for numpy)
2. Call `flat_law(flat_numpy_array, ...)` — then `_python_gravity_flat_law`
   receives a numpy array and tries to do `len(data)` etc., which works for
   numpy arrays but not for numba typed lists, and more importantly does not
   use the pedagogical for-loop path properly.

The 4 hand-crafted tests bypassed this by passing Python lists directly.

### Why System can't be created with python engine

`System.__init__` does `self.D = self.data.shape[2]` and uses
`self.data.__array_namespace__()` — both require array API compliance that
Python lists don't provide. So `ScenarioFactory(engine='python').create_scenario(...)`
fails. This is the fundamental reason scenarios must be created with numpy.

### The conversion strategy

When `TrueLawModel(factory=ScenarioFactory(engine='python')).law(system)` is
called (where `system` was created with numpy):
1. `law()` override detects python engine
2. Converts `system.data`, `system.masses`, `system.immobile` via
   `to_numpy_host(...)` (handles any backend) then `.tolist()`
3. Calls `_python_gravity_flat_law(data, masses, immobile)` with Python lists
4. Returns `np.array(result).reshape(numpy_data.shape)` — numpy array for
   compatibility

Similarly for `flat_law()`.

### Test strategy

- `ENGINES_WITH_PYTHON_LAW` = all engines in `ENGINES_TO_TEST` plus python
  (and numba if available from `get_available_engines()`)
- `test_law_scatter_3D` parametrizes over `ENGINES_WITH_PYTHON_LAW`
- For python/numba: `scenario_engine = 'numpy'` (create system with numpy),
  `law_factory = ScenarioFactory(engine=engine)` (law uses python engine)
- For other engines: system and law both use the same engine
- `test_law_vectorised` stays on `ENGINES_TO_TEST` — vectorised calling over
  multiple systems simultaneously is a numpy/JAX feature, not the python law

## Key Decisions

1. **`_to_py_list` helper**: Extracts the repeated conversion pattern
   `to_numpy_host(np.asarray(x)).ravel().tolist()` into one place.
2. **Return numpy array from python path**: Both `law()` and `flat_law()` for
   python engine return numpy arrays, keeping the API consistent with the
   numpy path. This means `.shape`, `.reshape()` work on all outputs.
3. **Remove 1-D only note**: Was misleading; the limitation wasn't enforced
   and doesn't need to be documented at this stage.
4. **Keep vectorised test numpy-only**: Vectorised calling (batch over C
   systems) requires `__array_namespace__()` and multi-system reshaping — a
   numpy/JAX feature. The python law isn't expected to support this.
