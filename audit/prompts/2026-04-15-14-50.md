# Prompt Record: Move visualization code and keep CLI args local (2026-04-15)

## User requests

The user first requested:
- move convergence video code from `entry.py` into a new `visualisations/convergence.py`
- move the existing visualization code there too

Then the user refined the architectural requirement:
- inspect functions driven by `entry()` outside `entry.py`
- make parameter lists more explicit
- do not allow the parsed CLI namespace (`args`) to leave `entry.py`

Finally, the user requested a commit of this refactor step.

## Decisions and reasoning

1. **Create a dedicated visualization package**
   - Added `teachgrav.visualisations` and placed the concrete visualization implementation in `teachgrav.visualisations.convergence`.
   - This keeps visualization concerns out of `entry.py` and prepares a more coherent structure than growing `viz.py` indefinitely.

2. **Keep `viz.py` as a compatibility facade**
   - Existing code and tests import from `teachgrav.viz`.
   - Re-exporting from `viz.py` avoids a wider compatibility break while still allowing the real implementation to move.

3. **Keep the CLI namespace local to `entry.py`**
   - The main architectural cleanup was not just moving code, but ensuring the external convergence generator takes explicit parameters instead of `args`.
   - A small wrapper remains in `entry.py`, which is the correct place to translate CLI state into a stable API.

4. **Patch tests at implementation boundaries**
   - Tests that previously patched `teachgrav.entry.convergence_video` or `teachgrav.entry.integrate_trajectory` were updated to patch the new implementation module.
   - This preserves targeted regression coverage for the refactor.

5. **Focused verification only**
   - Used the convergence and viz test files for verification because they cover the moved code directly and keep the iteration cycle short.
