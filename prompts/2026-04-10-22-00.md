## Exploration and Key Observations

- `array_abstraction.py` had a single `ArrayAbstraction` class with large `if/elif/elif` chains in `configure_engine`, `seed_random`, `array`, and `random_array`.
- `engine_support.py` contains detection functions and engine name lists (`jax_engines`, `mlx_engines`, `torch_engines`, `valid_engines`). We chose **not** to modify it, keeping the scope minimal.
- `to_numpy_host` and `_ensure_torch_array_api` helpers were in `array_abstraction.py`; they needed to move to the engines subfolder.
- Callers (`scenarios.py`, `laws/gp.py`, `laws/pl.py`, `test_system.py`) all import from `array_abstraction`, so we needed a backward-compatibility shim there.
- Optional dependencies (jax, mlx, torch) must **not** be imported at module level — lazy imports inside methods only.

## Key Design Decisions

### Class hierarchy
- `BaseEngine(ABC)` in `engines/base.py` — defines the interface (`array`, `random_array`, `seed_random`, `np` attribute).
- Engine variants each in their own file; related variants share an intermediate base:
  - `JaxBaseEngine` → `JaxCpuEngine`, `JaxGpuEngine`, `JaxMetalEngine`
  - `MlxBaseEngine` → `MlxCpuEngine`, `MlxGpuEngine`
  - `TorchBaseEngine` → `TorchCpuEngine`, `TorchGpuEngine`, `TorchMpsEngine`

### Factory / metaprogramming
- `engine_name_to_class_name(name)`: capitalises each hyphen-separated segment and appends `'Engine'`.
  - `'jax-cpu'` → `'JaxCpuEngine'`
- `create_engine(name, seed=None)`: validates the name, derives the class name, looks it up in `globals()`, and instantiates it.

### Backward compatibility
- `array_abstraction.py` reduced to a shim that re-exports `to_numpy_host` and provides an `ArrayAbstraction` factory function delegating to `create_engine`.
- All existing imports continue to work without changes.

### MLX random
The original code used `mx.random.uniform` but then switched to NumPy RNG for reproducibility. We preserved this behaviour in `MlxBaseEngine.seed_random` / `random_array`.

### PythonEngine.random_array min/max
The original `random_python_matrix` always returned [0,1]; the new version correctly scales by `min`/`max`, which is more correct and consistent with other engines.
