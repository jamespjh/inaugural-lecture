# Prompts: Improve Scenario Abstraction via Classes

**Date**: 2026-04-10T22:00
**Issue**: https://github.com/jamespjh/inaugural-lecture/issues (Improve scenario abstraction via classes)

## User Instruction Summary

Replace the flat `scenarios.py` with a subfolder containing a base `Scenario`
class, individual subclasses for each scenario, and a factory (`ScenarioFactory`)
that uses metaprogramming (importlib) to go from a string name to the correct class.

The specific comment from jamespjh: "Use factory pattern to go from string scenario
names to the object to create, with appropriate metaprogramming to go from string
to classname."

## Key Decisions

### Metaprogramming approach
The naming convention chosen is: string `"foo"` → module
`teachgrav.scenarios.foo` → class `FooScenario`.  This matches the pattern used
in many Python plugin/extension registries and is simple to follow.  Using
`importlib.import_module` at call time means no global registry needs to be
maintained; the file system is the registry.

The `KNOWN_SCENARIOS` list in `__init__.py` exists purely for error messages
and argument-parser `choices=` – it is not used for dispatch.

### Module structure mirrors `laws/`
The `laws/` package already uses one-file-per-implementation with a factory
function in `laws/laws.py`.  The `scenarios/` package follows the same
structure (one file per scenario, factory in `__init__.py`).

### Backward compatibility
All existing callers use `from teachgrav.scenarios import ScenarioFactory,
STOCHASTIC_SCENARIOS`.  The new `scenarios/__init__.py` re-exports both
symbols, so no callers need to change.

### Removing the old scenarios.py
Python would prefer the package directory over the `.py` file, but leaving
both would be confusing.  The old file was deleted.

### No changes to tests
The existing `test_scenarios.py` tests continue to pass without modification
because the public API (`ScenarioFactory.create_scenario`) is unchanged.
